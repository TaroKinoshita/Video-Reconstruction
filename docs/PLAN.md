## 1. 目的

参考映像を、**後から触れる3Dシーン**（カメラ、配置、動き、タイミング）に変換する。さらに、その3Dシーンを構造の手がかりにして、動画生成モデル（V2V）で最終映像を作る。

```
参考映像 ──→ 編集できる3Dシーン（下書き） ──→ 最終映像（V2V）
               ↑ ここ自体にも価値がある         ↑ 3Dでの編集がここまで残るか
```

**【確定】ゴールは両方（C）**
1. **3Dの下書き**：参考映像のカメラワークと配置を、Blender上のデータとしてそのまま使える。previzの初稿、別アングルの検討などに使う。
2. **最終映像**：3Dで加えた編集（カメラ、物の差し替え、タイミング）を、生成後の映像に反映する。

最初の利用者は、Blenderで短いCGショットを作る個人クリエイター（自分）。

## 2. 研究の問い

**【確定】** 「AIがレンダーを見比べて直す」こと自体は新しくない（CineReconも同じ手順を取っている）。だから問いは次の2つにする。

| | 問い | 主に比べる場所 |
|---|---|---|
| **RQ1** | 構造化された診断と専用の修正ツールを与えると、通常のLLM＋MCPより、再構成の精度、編集しやすさ、費用が良くなるか | 元動画 ↔ 3Dレンダー |
| **RQ2** | 3Dで加えた編集が、生成後の映像にどこまで残るか。関係ない部分は保たれるか | 3D ↔ 生成映像 |

どちらも未検証の仮説。同じ映像、同じLLM、同じ予算で比べて確かめる（11章）。

## 3. 範囲と段階の考え方

**【確定】本番の入力は「シーン（複数カット）」**。寄りのカットだけでは空間の情報がないので、引きや切り返しのカットと合わせて1つの空間にまとめる必要がある。

ただし、いきなり複数カットは作らない。段階を踏む。

```
単一カット（部品の確認） → 重なりのある2カット → 複数カットのシーン → 出来事（人の動き）
```

- データ設計は最初から、複数カットを入れられる形にしておく。実装は後で行う。
- 目標は「本物の撮影空間を当てる」ことではない。**見えている証拠と矛盾が少ない、編集用の空間**を作ること。
- 映画特有の問題（切り返しのためにセットを動かす、アクションつなぎで同じ動作が重複する、映らない側がある）は、カットごとの差分と不確かさとして扱う。

初期の範囲外：複雑な人の演技、流体、破壊、長尺、HoudiniやAfter Effectsとの連携。

### 3.1 最初の完成地点（マイルストーン1）【確定】

段階2までで、一度「完成」と呼べる状態にする。複数カットやV2Vで詰まっても、成果が残るようにするため。

| | 完成の中身 |
|---|---|
| **M1-本体** | 短い単一カットを、編集可能なBlenderシーンに再構成する。診断と自動修正によって、条件B（素のLLM＋MCP）より改善することを、11章の方法で示す（RQ1） |
| **M1-V2V** | 別の実験として、3Dで加えた編集が生成映像に保たれるかを、11章の方法で検証する（RQ2）。結果が「保たれない」でも、測定できていれば完了とする |

M1の成果物：動くCLIとMCPサーバー、編集可能な `.blend`、評価結果（失敗例を含む）、費用と作業時間の記録、短い技術レポート。

## 4. 全体構成

### 4.1 役割の分担【確定】

| 部分 | 担当 | 差し替え |
|---|---|---|
| LLM（Claude / GPTなど） | 診断を読んで、原因の候補と次の作業を**提案**する | できる |
| 解析・診断プラグイン | 映像やシーンを測定して結果を返す | できる |
| 最適化ツール | 指定された範囲で、数値（位置、画角など）を探す | できる |
| 制作ツールの接続部分 | Blenderなどを操作する | できる |
| 生成モデル（V2V） | 制御入力から最終映像を作る | できる |
| **実行管理部分（自作）** | 工程、予算、中断と再開、修正履歴、候補の試行と採用・取り消しを管理する | 本体（固定） |
| **制約管理（自作）** | 人のロック、変更してよい項目、「手で変更した」と「ロック」の区別。違反した候補を不採用にする | 本体（固定） |
| **Blenderからの読み戻し（自作）** | 人がBlenderで変更した所を取り出して、人の修正として統合する（7.2.1） | 本体（固定） |
| 接続部分 | CLI、MCPサーバー、各モデルやツールへの接続 | できる |

- MCPは「AIに道具を見せるための接続規格」にすぎない。反復の計画、状態、予算、採用の判断は、実行管理部分が持つ。
- LLMはシーンを直接書き換えない。実行管理部分に「変更の提案」を出す。そうすれば、人のロックや予算のルールをLLMが破れない。
- LLMを途中で替えても、作業途中の状態と検証結果は残る。

### 4.2 全体の流れ

```
参考映像
  ↓
[解析] カット分割 / カメラ / 奥行き / 物体 / 動き   … 別環境で動かすプラグイン群
  ↓
[観測データ] ──→ [採用した再構成] ←── [人の修正・拘束]
                      ↓
               [Blenderビルダー] → .blend / 制御用の素材（奥行き・輪郭・領域・カメラ）
                      ↓                              ↓
               3Dレンダー                       [V2V生成] → 最終映像
                      ↓                              ↓
               [比較と診断 ①]                  [比較と診断 ②③]
                      ↓                              ↓
               [修正ループ]（5章） ←───────────────────┘
```

## 5. データ設計

### 5.1 データの4つの層【確定】

映像から得られるのは、誤りや曖昧さを含む推定。だから、どこかに書いたことを「事実」として扱わない。

| 層 | 中身 | 例 |
|---|---|---|
| 観測 | 解析結果をそのまま残す | 画面上の物の軌跡、推定した奥行き、カメラの候補 |
| 採用した再構成 | 今使っている制作状態 | 使うカメラ、形、配置、アニメーション |
| 人の修正・拘束 | 人が決めたこと。最優先 | 床の高さ、この物は動かさない、接触した時刻 |
| 成果物 | 作ったもの | `.blend`、制御用の素材、生成映像、比較結果 |

- 「採用した再構成」は、**今採用している制作状態の基準**であって、元映像の真実ではない。
- 解析をやり直しても、人の修正・拘束は上書きしない。
- **「手で変更した」と「今後変更禁止（ロック）」は別の情報として持つ。** 手で直したけど、AIがさらに調整してよい場合もあるため。
  - `edited_by_human`：人が変更した履歴（いつ、何を、どの値に）
  - `locked`：AIが変更してはいけない項目。人が明示的に付ける
- メッシュ、奥行き、大量の軌跡はJSONに詰めない。外部ファイルにして、ID・パス・ハッシュで参照する。

### 5.2 再構成の中身

| 区分 | 中身 |
|---|---|
| 共通セット | 部屋、大まかな家具の配置、人物・物体の識別情報 |
| カットごとのカメラ | 位置、向き、画角、カメラの動き |
| 出来事 | 人物や物体の動作、開始と終了、前後関係 |
| 編集情報 | カット順と、出来事の時間への対応 |
| カットごとの差分 | そのカットだけに必要な配置やポーズの補正 |
| 根拠と不確かさ | どのフレームから推定したか、何が未確定か、人が確定したか |

確信度はAIの自己申告（「80%」など）では持たない。根拠フレーム、観測された制約、人の確定で持つ。

### 5.3 時間の扱い【確定】

時刻は4種類を区別する。

| 時刻 | 意味 |
|---|---|
| 元動画の時刻 | 入力ファイルの何フレーム目か |
| カット内の時刻 | そのカットの何フレーム目か |
| 3Dの動作時刻 | 再構成した出来事がいつ起きるか |
| 編集後の時刻 | 完成映像のタイムライン上の位置 |

- カットが変わったとき、「動作が続いている」「時間が飛んだ」「同じ瞬間の別視点」のどれかを記録する。アクションつなぎで「二度座る」バグを防ぐため。
- 編集情報（カット順、尺）は、複数カットを扱う段階で OpenTimelineIO（`.otio`）を使う。単一カットの段階では、時刻の対応を明示するだけでよい。

### 5.4 入出力の約束（コントラクト）【確定】

モジュール同士の約束には、項目名だけでなく次の取り決めも含める。ここが曖昧だと、形式は合っていてもシーンがズレる。

- 座標軸（右手系か、どの軸が上か）と単位
- 行列の向き（camera-to-world か world-to-camera）、回転の表し方（クォータニオン、オイラー角の順番）
- フレーム番号の起点（0か1か）、フレームレート
- カメラの内部パラメータ（焦点距離、センサーサイズ、主点）

具体的な値は `docs/CONVENTIONS.md`（作成予定）にまとめる。

### 5.5 形式

- 管理データ：JSON。型は Pydantic で定義し、`schema_version` を付ける。
- 編集情報：OpenTimelineIO（複数カットの段階から）。
- USD：初期は書き出し先の1つにとどめる。理由はBlenderのUSD読み込みに制約（layers や references など）があるため。USD自体の問題ではない。Houdiniなどと連携する段階で、任せる範囲を見直す。

## 6. 修正ループ

### 6.1 流れ【確定】

```
LLMが原因の候補を提案（例：「カメラの画角が原因かも」）
  ↓
実行管理部分：人のロックと予算をチェック
  ↓
作業用コピーを作る（採用状態はまだ触らない）
  ↓
作業用コピーの上で：最適化ツールが数値を探す → 再レンダー → 診断
  ↓
制約と評価を確認（6.4）
  ├ 通過 → 採用状態に反映（スナップショットを残す）
  └ 不通過・失敗・中断 → 作業用コピーを捨てる。採用状態は変わらない
  ↓
止める条件まで繰り返す
```

**【確定】候補は試してから採用する**
- 修正の候補は、必ず作業用コピーの上で実行する。
- 採用状態に反映するのは、制約と評価の確認を通ったときだけ。反映は一度にまとめて行う（途中までの反映はしない）。
- 失敗、エラー、中断、予算切れになった処理は、採用状態を変更しない。中断した所から再開できるように、試行の記録は残す。

- 細かい数値の調整は、LLMに毎回考えさせない。LLMは「どこを疑うか」を選び、数値探しはツールが行う。
- 定型の操作（カメラを置く、物を配置する、キーフレームをずらす）は、自作の操作として用意する。
- 任意のPythonコード実行は最後の手段。実行したコードは保存して、再利用できるようにする。
  - 実行は作業用コピーの上だけで行う。
  - 実行後、実行前の状態と比べて変更点を全部取り出す。**ロックした項目の変更、または候補として宣言した範囲の外の変更が1つでもあれば、採用できない**（コードの事前検査だけには頼らない）。
- 同じ操作をやり直しても、物が重複して増えないようにする（冪等性）。

### 6.2 診断で測るもの

元動画からは、正しいカメラ位置や画角が1つに決まらないことがある。だから「真の誤差」は測らない。測るのは次のもの。

- 画像上の対応点のズレ（物ごと、フレームごと）
- 推定値と、その不確かさ
- 軌跡の差、動き出しの時刻の差
- 物理的なおかしさ（浮いている、めり込んでいる、接触がない）

「箱が右に20pxズレている」と分かっても、原因は物の位置、カメラの向き、焦点距離のどれもありうる。原因の切り分けは、LLMの候補と最適化の結果で行う。

### 6.3 比較の3か所【確定】

```
元動画 ──①── 3Dレンダー ──②── 生成映像
   └────────────③──────────────┘
```

| | 確かめること | 直す場所 |
|---|---|---|
| ① | 構図と動きが元動画と合っているか | カメラ、配置、アニメーション |
| ② | 生成映像が3Dの配置と動きを守っているか | 制御入力、生成設定、モデル |
| ③ | 見た目が元動画に近いか | 素材、照明、参照画像、生成設定 |

**ルール：②のズレを理由に3Dを直さない。** V2Vが勝手に動かした物に合わせて、正しい3Dを壊さないため。

### 6.4 採用の判断【確定】

「点が下がったら戻す」だけでは足りない。2段階で決める。

1. **守る制約**：人のロック、①の動きなど。破ったら不採用。
2. **評価項目ごとの比較**：構図、動き、見た目、費用、速度を別々に比べる。何を優先するかは、その回の目的で決める。

### 6.5 ルール

- 人がロックした物は、AIが変更できない。
- AIの修正には理由を残す（どの診断を見て、何を変えたか）。研究のデータにもなる。
- 予算（回数、時間、API費用）と止める条件を決める。上限に来たら止めて報告する。
- 修正ごとにスナップショットを残して、いつでも戻せるようにする。

## 7. インターフェース

### 7.1 層の構成【確定】

```
Claude Code ─┐
Codex       ─┼─ MCP ─→ vrecon-mcp（自作）─┐
別のAI      ─┘                          ├→ vrecon本体 → Blender（版を固定）
人（コマンド）──────── vrecon CLI ────────┘
```

- **本体はPythonのコマンド（CLI）**。人もAIも、同じコマンドと保存データを使う。
- **MCPサーバー**は、CLIと同じ機能をAIに見せる入口。MCPは共通規格なので、Claude CodeでもCodexでも同じ道具が使える。
- **Claude Codeは操作役の1つ**。会話がなくても、保存データから作業を再開できる。

### 7.2 使い方

| # | 人がやること | 画面 |
|---|---|---|
| 1 | 動画と目標（「このカメラワークを再現」など）を渡す | Claude Code（またはコマンド） |
| 2 | AIが解析 → 3D化 → 修正ループを回す | — |
| 3 | 結果を見る：比較、推測の箇所、AIの修正履歴 | HTMLレポート（ファイル1枚、サーバーなし）、Blender |
| 4 | OKを出す / 方針を指示する / 必要なら手で直す | Claude Code、Blender |

- 人の役割は「目標と制約を決めて、最後に判断する」。直す作業は基本的にAIとツールが行う。
- 人がBlenderで手で直した場合は、それを「人の修正」として読み戻す。**この仕組みは最初から作る。**

### 7.2.1 人の修正の読み戻し【確定】

```
vrecon handoff  … 人に渡す時点の状態を保存（これが比較の基準）
   ↓ 人がBlenderで編集
vrecon ingest   … 基準と比べた差分だけを「人の修正」として取り込む
```

- **比較の基準は「人が編集を始めた時点の保存状態」**。生成時の状態と比べると、その後のAIの変更まで人の変更と誤認するため。
- 人の編集中は、AIはその `.blend` を変更しない。
- **初期に読み戻す範囲**（これ以外の変更は警告して取り込まない）：
  - ID付きの物体の位置、回転、拡縮
  - カメラの設定（位置、向き、焦点距離、センサーサイズ）
  - 上の項目に対応するキーフレーム
- 後回し：形状の編集、モディファイアの変更、素材、新しく追加された物体。
- 読み戻した変更は `edited_by_human` に記録する。ロックにするかは人が別に指定する（5.1）。

### 7.3 段階ごとの画面

| 段階 | 画面 |
|---|---|
| 初期 | Claude Code＋CLI＋Blender＋HTMLレポート。専用UIは作らない |
| 流れが固まったら | Blenderアドオンのパネル：推測の一覧、ロックと確定のボタン、工程の実行 |
| 他人が使う段階 | そのとき専用UIを検討する（Webも選択肢） |

Webアプリは今は作らない。理由は、処理の流れが固まる前にUIを作ると、作り直しが増えるため。

## 8. モジュールと候補のOSS

**【確定】** 研究・非営利なので、非商用ライセンスの重みも使ってよい。ただし、モジュールごとにライセンスを記録する。重みは再配布しない。デモや論文を公開するときは、各ライセンスの条件を確認する。

| 用途 | 候補 | ライセンス（記載されている内容） |
|---|---|---|
| カット分割 | PySceneDetect（CPUで動く）、TransNetV2（精度が高い）、AutoShot | — |
| カメラと画角 | MapAnything、MegaSaM、VGGT、Pi3 | MapAnythingは通常版の重みがCC BY-NC、Apache版もある。MegaSaMのコードはApache 2.0。VGGTとPi3の標準の重みは非商用 |
| 奥行き | Video Depth Anything | SmallはApache 2.0、Base/LargeはCC BY-NC 4.0 |
| 物体の3D化 | SAM 3D Objects | 独自のSAM License。商用禁止の条文はない。再配布の条件、軍事用途の禁止などがある |
| 人の動き | GVHMR | 教育、研究、非営利の目的に限る |
| 複数カットの位置合わせ | COLMAP（重なりのある画像からの復元）、Multi-THuMBS（人物を対象にカット境界をまたいで復元） | Multi-THuMBSはコードの公開を確認できていない |

GPUの目安（参考）：Video Depth Anything の公式表では、A100、入力1×32×518×518の条件で、Smallが約7GB、Largeが約24〜27GBのVRAM。これは測定条件つきの数字で、最低要件ではない。

自作するもの：
- 実行管理部分（状態、制約、予算、履歴、採用・取り消し）
- 共通データ → Blenderビルダー、Blenderからの読み戻し
- 診断ツール（重ね合わせ、対応点のズレ、軌跡、接地・めり込み）
- 最適化ツール（カメラ、配置、タイミングの数値探索）
- MCPサーバー、HTMLレポート
- 後の段階：複数カットの統合

## 9. V2Vの層

**【検討中】** 既存のモデルをそのまま使うか、モデルを少し改造してシステムに合わせるか（Matrix-Game 4.0のように、簡略化したレンダーを詳細な映像に変える方式）は、これから決める。

| 選択肢 | 例 | 特徴 |
|---|---|---|
| 既存のAPIモデル | MiniMaxなど | 手軽。構造の制御（奥行きなど）を受け付けるかが問題。**MiniMaxの対応状況は未調査** |
| 制御に対応した公開モデル | Wan2.2 Fun Control など | 奥行きやポーズで制御できる。GPUが必要 |
| システム向けに改造・追加学習 | Matrix-Game方式 | 制御を守りやすくなる可能性がある。学習データと計算資源が必要 |

どれを選んでも困らないように、こちら側で次のことをしておく。
- 3Dシーンから制御用の素材（奥行き、輪郭、物体ごとの領域、カメラの数値）を毎回書き出して保存する。
- 生成モデルは差し替え式のモジュールの1つにする。モデル名、版、シード、設定を記録する。
- ②の比較（3D ↔ 生成映像）で、制御がどこまで守られたかを測る。

改造や学習は、既存モデルで②を測って足りないと分かってから検討する。

## 10. 差し替えと互換性

1. **データの版**：`schema_version` を付ける。変えたら変換スクリプトを用意して、古いデータも読めるようにする。
2. **モジュールの宣言**：各モジュールは、入力、出力、対応するデータの版、5.4の取り決めを宣言する。本体は設定ファイル（`configs/modules.yaml`）を見て、どれを使うか選ぶ。
3. **実行環境の分離**：OSSごとに要求するPythonやCUDAの版が違う（例：MegaSaMの記載はPython 3.10＋CUDA 11.8）。重い解析モデルは、必要に応じて専用の環境で別プロセスとして動かし、ファイルでやり取りする。本体はPythonの通常プロセスで動かす。Blenderの操作は、版を固定したBlender（`bpy` 5.2.3はPython 3.13専用）で行う。
4. **版の固定**：モジュールごとにロックファイル（`uv`）かコンテナを持つ。`bpy` を呼ぶコードはビルダー1か所に閉じ込める（Blenderは5.xでAPIが変わっている）。
5. **出所の記録**：どのモデル、重み、版、ライセンス、設定で出した結果かを残す。
6. **回帰テスト**：決まったテスト映像で毎回評価する。採用するかは、品質、費用、速度、編集しやすさを別々に比べて決める。
7. **LLMは状態を持たない**：途中経過は全部データに残る。指示文はモデルごとに調整が要ることがある。

## 11. 評価

### 11.1 比較する条件

| 条件 | 内容 | 主な問い |
|---|---|---|
| A 直接生成 | 参考映像と編集指示を、そのままV2Vモデルに渡す | RQ2の基準 |
| B LLM＋MCP | 素のLLM＋Blender MCPで再構成し、同じ生成工程に通す | RQ1の基準 |
| C 提案手法 | Bに、構造化された診断、最適化ツール、実行管理を加える | RQ1、RQ2 |
| Cの部品外し | 効果が出たら、診断や最適化を1つずつ外して寄与を測る | どの部品が効いたか |

- BとCは同じLLM、同じ生成モデル、同じ予算で比べる。
- 費用と人の介入時間も記録する。

### 11.2 測るもの

- 編集の成功（頼んだ変更が反映されたか）
- 画面上の軌跡の誤差、出来事の時刻の誤差
- 関係ない部分が保たれたか（編集の正当な結果、例えば隠れ方の変化は、採点前に定義しておく）
- 見た目の近さ
- 実行の費用、時間、修正の回数
- 人の手直し時間

### 11.3 RQ1の判定方法（M1-本体）【確定：方法／検討中：数値】

**主張を2つに分けて、事前に決めておく**
| | 主張 | 比べ方 |
|---|---|---|
| **H1a（主）** | 同じ予算で、BよりCの精度が高い | 同じLLM、同じ予算の上限で、最終的な精度を比べる |
| **H1b（副）** | Bと同じ精度に、Cはより安く・速く届く | Bの最終精度に届くまでの費用、時間、修正回数を比べる |

**精度として測るもの（元動画 ↔ 3Dレンダー）**
- 追跡した対応点の、画面上の再投影誤差（ピクセル、画面の対角長で正規化）
- 物体ごとの領域の重なり（IoU）と中心の軌跡の誤差
- 出来事の時刻の誤差（フレーム数）
- 編集しやすさ：決めた編集作業（カメラの変更、物の差し替え、タイミングの変更）が、シーンを壊さずにできるか

**判定**：検証用の映像で、H1aの主な指標がBを上回ったクリップの数と、差の中央値を報告する。どの差を「改善」と呼ぶかの基準値は、11.6の手順で事前に固定する。

### 11.4 RQ2の判定方法（M1-V2V）【確定：方法／検討中：数値】

編集の種類ごとに、生成映像を同じ解析ツールで測り直して、3Dと比べる。

| 編集 | 成功とする測り方 |
|---|---|
| カメラの移動 | 生成映像から推定したカメラの軌跡と、3Dのカメラの差（回転の角度差、移動方向の差、画角の差） |
| 物体の移動・差し替え | 生成映像を領域分割して、3Dの物体の領域とのIoU、中心の軌跡の誤差 |
| タイミングの変更 | 出来事の開始時刻の差（フレーム数） |
| 関係ない部分の保持 | 編集していない物体の軌跡のズレ、編集していない領域の見た目の差 |

- 条件A（直接生成）と同じ指標で比べる。
- 編集の正当な結果（例：物を動かしたら隠れ方が変わる）は、採点の前に定義しておく。

### 11.5 試行回数とばらつき【確定】

- 生成も再構成も結果がばらつくので、**1条件につき3回以上**試す（シードを変える）。シードは全部記録する。
- 失敗した試行も除外しない。成功率と中央値を報告する。
- 本数：M1は開発用6本、検証用6本の単一カットを基本とする（予備実験の結果で見直してよい。ただし11.6の固定より前に限る）。
- これは探索的な研究であり、統計的に有意な一般的優位性の主張はしない。

### 11.6 基準の事前固定【確定】

1. 開発用の映像だけで、小規模な予備実験をする。
2. その結果から、各指標の成功の基準値、予算の上限、試行回数を決める。
3. 決めた値を `evaluation/thresholds.yaml` に書いてコミットする。**このコミットより後に、検証用の映像を初めて使う。**
4. 検証用の映像で結果を出したあとに、基準値を変えない。変えた場合は、その事実と理由を報告する。

### 11.7 映像

- 開発用と、調整に使わない検証用に分ける（提案書の案は12本：6本と6本）。同じ元映像から派生したクリップは、同じ側に入れる。
- CineReconの公開データ（50本、360クリップ、11カテゴリ）を基準点に使えるか検討する。ただしコードと注釈はMITでも、**動画の著作権は権利者のもの**なので、使える範囲を確認する。
- 前の検討で出たCineReconの数値（修正ループの有無で66.4→76.6、項目別の点数）は **【未確認】**。論文で確認できるまで使わない。

### 11.8 採点の物差しと修正の道具を分ける【確定】

条件Cが修正に使う解析ツールと、採点に使う物差しが同じだと、自分で測って自分で合格を出すことになり、点数が実力以上に良く見えるおそれがある。

- 採点には、修正に使うものとは別の手法を使う。
- 一部のクリップには、人が確認した正解データ（対応点、物体の領域、出来事の時刻）を用意して、物差し自体の誤差も確かめる。
- どの指標をどの手法で測ったかを、結果と一緒に記録する。

## 12. 段階と進む条件

ゴールがCなので、最初は2本の線を並行して進める。

| 段階 | 中身 | 進む条件（判定方法） |
|---|---|---|
| 0 準備 | `bpy` が動くか確認、データの型と取り決め（5.4）、CLIの骨組み、`handoff`/`ingest` の最小版 | 決めた手順でシーンを作ってレンダーでき、読み戻しのテスト（7.2.1の範囲）が通る |
| 1a V2Vの制御テスト | 手作りの簡単な3Dシーン → 制御用の素材 → V2V。カメラ、物、タイミングを1つずつ変える | 11.4の指標で、3種類の編集それぞれの成功率を測り終える。基準値に届かない種類があれば、生成の方式を見直してから自動化に進む |
| 1b 単一カットの基準点 | 条件B（素のLLM＋MCP）で開発用の映像を再構成し、11.3の指標を測る | 開発用6本×3回の結果がそろう |
| 予備実験と固定 | 開発用の映像で基準値、予算、試行回数を決める | `evaluation/thresholds.yaml` をコミット（11.6） |
| 2 診断と修正ツール | 条件C（診断、最適化、実行管理、候補の試行と採用）を作り、検証用の映像でBと比べる | 11.3の判定を検証用6本×3回で実施し終える → **M1-本体の完了**（結果が否定的でも、報告できれば完了） |
| **M1** | M1-本体＋M1-V2V（3.1） | 技術レポートと評価結果がそろう |
| 3 重なりのある2カット | 同じ場所を撮った2カットを、1つの空間にまとめる | 両カットで共通に見える点の再投影誤差が、事前に決めた基準値以下（基準値は段階3の開始時に固定） |
| 4 複数カットと出来事 | シーン単位の統合、出来事の時間軸 | 段階3の完了時に判定方法を決める |
| 後で | V2Vの改造・学習、Blenderアドオン、他のアプリ連携、事例の再利用 | それぞれ、効果が測れたら |

段階1aと1bは並行して進める。GPUの準備状況に合わせて順番を入れ替えてもよい。

### 12.1 解析OSSと自作MCPを入れる時期【確定】

OSSは一度に集めない。その段階で必要な分だけ入れる。

| 段階 | 解析OSS | MCP |
|---|---|---|
| 0 | なし | なし（CLIだけ） |
| 1a / 1b | **採点用**：点の追跡、物体の領域分割、カメラ推定（生成映像と再構成を測るため） | 既存の `blender-mcp`（条件Bは素のLLM＋MCPなので、自作の道具を混ぜない） |
| 予備実験 | 採点用ツールの設定を固定する | — |
| 2 | **再構成用**：カメラ、奥行き、物体（条件Cの診断と修正の材料） | **自作の `vrecon-mcp`**：診断、数値探し、候補の試行と採用 |
| 3 | 複数画像の位置合わせ（COLMAP、MapAnythingなど） | 統合用の道具を追加 |
| 4 | カット分割、人の動き（GVHMRなど） | 出来事用の道具を追加 |

同じOSSでも、段階1では「物差し」、段階2以降では「道具」として使う。両者の分け方は11.8に従う。

## 13. 開発と運用

- **クラウドセッション**：コードを書く、テストする、GitHubにpushする。BlenderのGUIとGPUはない。
- **ローカルPC**：実際に使う場所。Blender、GPU、ローカルのClaude Codeがある。
- **やり取り（パターンA）**：クラウドでpush → ローカルでpullして実行 → 結果（小さいファイルと一覧だけ）をpush。
- 動画や大きいファイルはGitに入れない。置き場所は別に決める（【検討中】）。
- このクラウド環境では、`arxiv.org`、`huggingface.co`、`cinerecon.github.io` が拒否された。モデルの重みのダウンロードや論文の確認が必要なら、環境の設定で許可する。

## 14. リスクと対応

| リスク | 対応 |
|---|---|
| V2Vが3Dの構造を守らない | 1aで先に確かめる。制御の条件やモデルを見直し、範囲を狭める |
| 解析の精度が低く、手直しが多すぎる | 不確かさを見せて、人が確定できるようにする。診断で原因を絞る |
| 複数カットが1つの空間にまとまらない | 無理に統合しない。カットごとの差分と、空白・推測として持つ |
| モジュールの更新で壊れる | 版の固定、取り決め（5.4）、回帰テスト |
| 部品を足しすぎて重くなる | 効果を測って、効かない部品は外す |
| 評価用の映像の権利 | 出所と利用条件を記録する。条件が不明なものは分けておく |
